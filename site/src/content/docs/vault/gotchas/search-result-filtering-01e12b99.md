## Summary

A topic-filtering safeguard was added to the JSON output contract (`buildQueryResults` in `json.ts`) to prevent topic pages from reaching the Obsidian plugin until v0.2.0 ships a coordinated enum extension. The MCP server (`mcp/server.ts`) is a sibling consumer of the same search hits and must also filter topics to avoid breaking the plugin's rendering and exposing unfinished content across different interfaces.

## What Was Learned

**Output contract isolation is incomplete across consumers.** The `json.ts` module filters `type: "topic"` and `topics/` directory hits before serializing to the wire schema, but `mcp/server.ts` directly consumes raw `SearchHit[]` from the retriever without the same safeguard. This creates a fanout gap: topics filtered from the CLI plugin will still appear in MCP consumers (e.g., IDE integrations), breaking the coordinated rollout assumption.

**Frontmatter parsing is duplicated.** Both `json.ts` (lines 71–91) and `mcp/server.ts` (line 75) implement identical minimal YAML parsers with the same kebab-flat behavior and quoting logic. This duplication compounds maintenance risk when the wire contract changes.

**Topic pages are work-in-progress and incomplete.** The comment explicitly notes that the plugin's category enum has no `topic` member, indicating topics are generated by `vir compose` but not yet fit for user-facing display. Safe degradation relies on the Recent tab scanning vault frontmatter independently, which does not filter.
